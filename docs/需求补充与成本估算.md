## 一、算力消耗 / 成本估算

### 1. 生成这个 App 的算力成本

| 口径 | 估算 | 说明 |
| --- | --- | --- |
| Token 用量 | 约 **150 万 – 350 万** tokens（输入+输出合计） | 实际产出：22 个 Dart 文件约 5,700 行，加上 iOS/Android 原生入口、4 个工具脚本、文档；过程中还有多轮编译日志、12 张截图核对与 3 次问题定位（中文路径导致着色器编译失败、package_config 失效等），输入侧因多轮上下文重复计费，通常是输出的 10 倍以上 |
| 国内模型 API 费用 | 约 **¥8 – ¥50** | 按输入 ¥1–4 / 百万 tokens、输出 ¥8–16 / 百万 tokens 量级估算 |
| 国际前沿模型 | 约 **$15 – $80** | Claude Sonnet / GPT 一类；用最贵的推理模型可能到 $150+ |
| 人力折算 | **2 – 4 人日**，约 ¥4,000 – ¥12,000 | 一名 Flutter 工程师按需求实现 + 联调 iOS |

要点：

- **App 运行本身几乎不耗算力**：纯本地存储、无后端、无 AI 调用，一个月 200 笔账对手机来说可忽略。
- 真正花钱的是**生成代码**这一步，以及后续每次改需求的对话。
- 如果以后加「AI 自动识别账单/语音记账」，单次识别约 500–2,000 tokens，
  按每月 100 笔算，API 成本 **¥0.1 – ¥2/月**，仍然很低；这类功能贵的是接入与调试，不是调用本身。

### 2. 这个数字为什么是区间
- 需求文本里的「付款/收款自动记录」在 iOS 上做不到真正自动，最后的实现方式会显著改变工作量；
- 是否要上架（App Store 审核、隐私清单、图标素材）会让工作量翻倍；
- 是否要接 Android 通知监听（原生代码）也是一档额外成本。

## 二、文本里还没说、但必须定的地方

### A. 数据从哪来（最容易低估的一块）

| 方案 | iOS | Android | 成本 |
| --- | --- | --- | --- |
| URL Scheme + 快捷指令一键记账 | ✅ 可用 | ✅ 可用 | 低（已实现） |
| 复制短信/通知文本 → 识别入账 | ✅ 可用 | ✅ 可用 | 低（已实现） |
| 支付宝/微信/银行 CSV 账单导入 | ✅ 可用 | ✅ 可用 | 中（已实现） |
| 截图 OCR 识别金额 | ✅ 需 Vision + 分享扩展 | ✅ ML Kit | 中高 |
| 通知监听自动抓取 | ❌ 系统禁止 | ✅ NotificationListenerService | 高（原生） |
| 读短信内容 | ❌ 基本不可行 | ⚠️ 需权限，商店审核敏感 | 高 |

**结论**：iOS 上「零输入」只能靠链接、剪贴板、账单；文本里「付款或收款就有记录」的期望需要提前对齐。

### B. 记账口径（决定统计准不准）

1. **退款 / 报销**：算收入还是冲减支出？两者会让「总支出」差很多，建议退款冲减原分类。
2. **信用卡还款 / 内部转账**：必须「不计收支」，否则支出翻倍。
3. **借贷与代付**：帮别人付的钱是「应收」不是支出。
4. **收入口径**：工资是税前还是税后？奖金、公积金、报销要不要计入。
5. **预算口径**：预算只扣支出，还是「支出 − 收入」？剩余是「预算 − 支出」还是「收入 − 支出」？
6. **周期账**：房租、订阅、话费、房贷要自动生账吗（这次未做，建议下一步）。
7. **账期**：发薪日不是 1 号时，按自然月还是按发薪周期统计。

### C. 预算要做多细

- 只要「总额度」就够，还是要**分类预算**（餐饮 1,500 / 交通 500）？
- 是否需要**结转**（本月没花完的额度留到下月）、**周预算**、**弹性预算**（80% 提醒）？
- 超支后的交互：只提醒，还是冻结某类消费提示？
- 换月时的默认值：沿用上月、还是重新输入？

### D. 分类体系（对应原文的「三维分类」）

原文的类别 / 账本 / 标签三维，这次实现的是「类别 + 备注 + 来源」。
如果真要三维：

- 二级分类（餐饮 → 早餐/外卖/咖啡）会让统计更好看，但录入变慢；
- 账本（日常 / 旅行 / 装修）需要「切换账本」的入口，否则用户不会用；
- 标签适合「临时项目」（婚礼、搬家），要支持多选和检索。

建议：先用一级分类 + 备注跑一个月，再决定要不要加维度。

### E. 数据与隐私

1. 数据只在本机 → **换手机就会丢**，需要导出/导入，或 iCloud 同步（要 Apple 开发者账号 + CloudKit）。
2. 上架需要：隐私政策、隐私清单（Privacy Manifest）、App 图标、启动图、TestFlight 测试。
3. 涉及金融信息的 App 在中国区上架，苹果通常要求说明数据用途，但记账类一般不要求金融牌照；
   若以后接支付、代扣，就进入监管范围。

### F. 体验细节（决定「懒人」是否成立）

- 一笔账要在 **3 秒内**记完：默认分类、默认时间、金额键盘、保存即回首页。
- 误删要能撤销（已做：删除后 SnackBar 可撤销）。
- 空状态要引导（已做）。
- 暗黑模式对比度、色盲友好的分类配色（当前用色相 + 图标双编码）。
- 首页数字要用等宽数字，避免跳动（已做）。

### G. 面向「养老 / 待业测算」还需要的能力

原文说这套方法可以用来测算养老或待业资金，那 App 还缺：

1. **固定支出清单**（房租、保险、月供）与**可变支出**分开统计；
2. **现金流预测**：按当前月均支出，算「存款能撑几个月」；
3. **安全边际**：待业期间每月最低生活成本 vs 可支配现金；
4. **被动收入覆盖度**：理财/租金收入占支出的比例。

这三项用现有数据两天内能加上，是最贴合原文目标的增值点。

## 三、建议的优先级

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| P0 | macOS 上跑通 iOS 模拟器 + 验证 `qingzhang://` 深链 | 目前只在 Web 上验证过界面，iOS 原生入口未实机验证 |
| P0 | 确定退款 / 转账 / 信用卡的口径 | 口径不定，统计数字就不可信 |
| P1 | 分类预算 + 周期账（房租/订阅） | 懒人记账的核心是「别让我每月重输」 |
| P1 | 现金流预测（待业能撑几个月） | 最贴合原文「养老/待业测算」 |
| P2 | 截图 OCR、Android 通知监听 | 体验提升，但工程成本高 |
| P2 | iCloud 同步、CSV 导出 | 换机不丢数据 |
